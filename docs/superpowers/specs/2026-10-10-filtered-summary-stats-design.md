# 过滤结果联动统计设计

日期：2026-10-10

## 目标

让文件审阅页右侧摘要统计与左侧的有效文件过滤保持一致。用户通过路径、文件名搜索或“仅新增”缩小范围后，右侧文件数、新增行和删除行只统计当前过滤范围，不再始终显示整个分支比较的总量。

已读/未读是阅读进度，不是代码范围过滤，因此不得改变右侧统计。

## 过滤语义

页面使用两层派生结果：

1. `summaryFiles`：从完整的 `comparison.files` 应用路径前缀、文件名搜索和“仅新增”状态过滤。
2. `visibleFiles`：从 `summaryFiles` 继续应用“未读”阅读状态过滤，用于左侧实际可见文件列表。

对应行为如下：

| 条件 | 左侧文件列表 | 右侧摘要统计 |
| --- | --- | --- |
| 路径前缀 | 影响 | 影响 |
| 文件名搜索 | 影响 | 影响 |
| 仅新增 | 影响 | 影响 |
| 未读 | 影响 | 不影响 |
| 文件被标记已读 | 可能从未读列表消失 | 不影响 |

## 统计计算

右侧摘要从 `summaryFiles` 派生：

- 文件数：`summaryFiles.length`
- 新增行：所有文件 `additions` 之和
- 删除行：所有文件 `deletions` 之和
- 增删比例条：使用过滤后的新增行与删除行计算

过滤结果为空时统一显示 `0 文件`、`+0`、`−0`，比例条不突出任一侧。清空路径、搜索和“仅新增”后，统计自然恢复为完整比较总量。

左侧“审阅目录”仍保留“当前可见文件 / 全部文件”的阅读提示；右侧摘要中的文件数表示当前统计范围。两者在启用“未读”时允许不同，因为前者包含阅读进度，后者不包含。

## 实现边界

- 不修改 Git API 或比较响应结构；现有每个文件已包含 `additions`、`deletions` 和 `status`，客户端可以直接聚合。
- 不发起额外请求，过滤和统计继续即时在浏览器内完成。
- 不改变文件选择、差异加载、已读标记和提交关系图行为。
- 将纯过滤与聚合逻辑提取为可单元测试的函数，组件只负责组合当前状态和渲染结果。

## 验证

- 路径过滤只统计匹配路径的文件及其增删行。
- 文件名搜索只统计匹配名称的文件及其增删行。
- “仅新增”只统计新增文件及其增删行。
- 多个有效过滤条件同时存在时取交集。
- “未读”切换以及已读集合变化不改变摘要统计。
- 空结果显示零值，清空过滤恢复完整总量。
- 原有构建、lint 和完整测试继续通过。
